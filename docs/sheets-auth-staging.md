# Проверка доступа по таблицам

Шаг D-02b после [подтверждённого переноса пользователей](evidence/2026-09-03-users-import-applied.json). Сервер умеет определять роль по Users и WorkspaceMembers для выбранной книги. Переключение выполняется владельцем после проверки переноса; до этого действует существующий staging-реестр.

## Подтверждённый результат

3 сентября в 14:37:18 владелец выполнил активацию: `ok: true`, `result: enabled`, `backend: sheets`, 2 пользователя и 2 членства. После этого он подтвердил работу доступа владельца и читателя. [Лог и границы подтверждения](evidence/2026-09-03-sheets-auth-activated.json). D-02b завершён; повторять активацию и проверки переноса не нужно. Далее — [раздел участников](workspace-admin.md).

## Порядок первоначального включения

Переключение опубликовано в серверной версии **5** из `68e61d6`, исходники редактора и снимок версии проверены через Google API. На прежнем `/exec` успешно проверены health, отказ неверному токену и запрет внешнего запуска активации. [Историческая запись публикации до активации](evidence/2026-09-03-sheets-auth-release.json). Инструкция ниже сохранена для первого включения; на текущем staging оно уже выполнено.

1. Обновить редактор рабочего **Tastory - Staging API**.
2. Выбрать **activateStagingSheetsAuth** и выполнить один раз. Ожидается `ok: true`, `result: "enabled"`, `backend: "sheets"`, `users: 2`, `memberships: 2` для текущего staging.
3. Открыть [настройки Tastory](https://kaerna-group.github.io/tastory/#/settings) под владельцем и нажать **Проверить доступ**. Затем проверить вход читателя: роли должны остаться owner и viewer.
4. Прислать JSON активации и результат проверки доступа. При `ok: false` остановиться и прислать безопасный код ошибки.

Повтор функции допустим и возвращает `already-enabled`, без повторной записи настройки. Повторять настройку схемы или перенос пользователей не нужно. Google ID и содержимое таблиц присылать не требуется.

## Что проверяет переключение

- Окружение staging, существующие ресурсы, схема 1, завершённый перенос и корректный реестр таблиц.
- Единственную книгу при первой активации. Её UUID записывается в настройку; выбор роли всегда ограничен этой книгой.
- Email эффективного пользователя редактора совпадает с перенесённым активным владельцем. Членство владельца также должно быть активным.
- Текущий реестр и строки совпадают с завершённым переносом. Изменения между переносом и активацией требуют разбора.
- Нет действующего непринятого приглашения из старого реестра. Его автоматическое принятие будет частью следующего шага управления участниками; в таком случае переключение останавливается с `PENDING_INVITATIONS`.

Проверки и запись выполняются под общей ScriptLock. Одним свойством `SHEETS_AUTH_CONFIG` сохраняются версия формата, backend и UUID книги; запись читается обратно. Адреса и Google sub не попадают в отчёт. Функция не создаёт пользователей, не меняет их роли, не отправляет письма и недоступна через HTTP.

## Работа после активации

Google JWT по-прежнему проверяется по подписи, issuer, audience и сроку действия. Проверенный `sub` сопоставляется с `Users.google_sub`; внутренний UUID пользователя используется для поиска его членства в выбранном workspace. Совпадение email без совпадения `sub` не даёт доступа.

Каждый запрос заново читает Users, Workspaces и WorkspaceMembers. Активный пользователь с активным членством получает роль из таблицы. Отсутствующее или отключённое членство, disabled/pending пользователь и неизвестная личность получают `ACCESS_DENIED`. Viewer не получает доступ к существующим операциям, разрешённым только владельцу.

Чтение ограничено 10 пользователями, 10 книгами и 100 членствами. Проверяются точные заголовки, типы, положительные ревизии, уникальность UUID/Google sub/email и пар членства, ссылки и соответствие владельца книги. Формулы, повреждение схемы, незавершённый перенос, maintenance mode и ошибки сервиса дают `AUTH_UNAVAILABLE` без использования старых приглашений. Кэшируется только проверочный материал Google, членство не кэшируется.

При отсутствии `SHEETS_AUTH_CONFIG` сервер до переключения использует прежний staging-реестр. При наличии настройки, даже повреждённой, ошибки Sheets не включают прежний способ входа. После активации не удалять эту настройку как способ восстановления: откат требует сначала согласовать актуальные права со старым реестром.

После активации `STAGING_INVITES`, `STAGING_AUTH_BINDINGS` и `setupStagingAuth` больше не управляют доступом выбранной книги. Старые инструкции отзыва через удаление элемента Script Properties применимы только до переключения. Следующий шаг добавит управление участниками и приглашениями из приложения с ревизиями и аудитом; вручную исправлять привязки для нового сценария не нужно.

## Совместимость и границы

Текущий auth/spike API сохраняет прежний непрозрачный `user.id` в ответе, чтобы не изменить принадлежность уже принятых приватных материалов и квитанций. Внутри проверки прав используется UUID из Users. Для будущих продуктовых действий будет отдельный контракт с workspace и внутренними ID.

Формат API v1, транспортный `schemaVersion: 0` и диагностический `health.storage` пока прежние. Проверка входа поддерживает схемы таблиц 1 и 2; переход на 2 выполняется при [подготовке журнала](operation-journal.md). Авторизованный `admin.health` проверяет соответственно 6 или 8 таблиц. Ответ имени и текущего email берётся из проверенного Google-токена, запись профиля и last_login_at этот шаг не выполняет.

Этот шаг допускает уже перенесённых пользователей. [Раздел владельца D-02c](workspace-admin.md) добавляет чтение участников и проверку структуры таблиц. Создание новых приглашений, принятие новых пользователей в Sheets, полный набор продуктовых разрешений, AuditLog и идемпотентность записей ещё не реализованы. Весь D-02 не закрыт.

## Проверки

Автотесты покрывают UUID/sub, роли по книге, отключение пользователя/участника, дубликаты и нарушенные связи, повреждённые данные, отсутствие возврата к старому реестру, владельца активации, повтор и потерянный ответ записи настройки. Собранный Apps Script проходит schema → import → activation → настоящий подписанный тестовый JWT → owner/viewer → отзыв → отказ при недоступном хранилище. Публичный вызов функции переключения отклоняется. Настоящий вход после активации подтверждается владельцем отдельно.
