# Вход Google и приглашения: staging

Обновлено 3 сентября 2026 года. Владелец выполнил настройку, Client ID подключён; auth API появился в deployment version 2, текущий сервер — version 4. Health подтверждает staging auth; отрицательные запросы к настоящему API проходят. Владелец подтвердил успешный настоящий вход и роль «Владелец» снимком интерфейса. Повторный вход, отзыв и остальные браузеры ещё требуют реального прогона. Полная схема Users/Invites и интерфейс управления участниками относятся к этапу 2.

**Для текущего владельца:** первый вход, фото и конкурентные записи приняты. Следующая проверка — [повторный вход, неприглашённый аккаунт и отзыв с экспортом отчёта](google-access-staging.md). К фото возвращаться не требуется. [Результаты auth](staging-verification.md#первый-настоящий-вход).

## 1. Создать OAuth client

1. Откройте [Google Cloud Console](https://console.cloud.google.com/) под владельцем Tastory. Создайте или выберите отдельный Cloud-проект `Tastory Staging`.
2. Откройте **Google Auth Platform**. Если требуется первичная настройка: название приложения `Tastory Staging`, контактный email владельца, аудитория **External**. Для тестового приложения добавьте нужные аккаунты в **Audience → Test users**, если консоль это предлагает. Эта настройка Google не заменяет приглашения Tastory.
3. В **Clients → Create client** выберите **Web application**, имя `Tastory Staging Web`.
4. В **Authorized JavaScript origins** добавьте `https://kaerna-group.github.io`. Путь `/tastory/` и завершающий `/` сюда не входят.
5. Для локальной проверки можно добавить `http://localhost` и `http://localhost:5178`, открывать сайт именно по localhost. Публикацию сначала проверяем на HTTPS Pages. Адрес с IP `127.0.0.1` не используем как OAuth origin.
6. **Authorized redirect URIs** оставьте пустым: выбран popup с JavaScript callback.
7. Скопируйте **Client ID** вида `…apps.googleusercontent.com` и передайте разработчику. **Client secret, пароль Google и JSON с credentials не нужны.**

Не используйте Client ID программы clasp. Менять Cloud-проект, связанный с Apps Script, ради этой настройки не требуется. [Настройка Google Identity Services](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid), [popup callback](https://developers.google.com/identity/gsi/web/reference/js-reference#callback).

## 2. Включить проверку на сервере

В рабочем отдельном проекте **Tastory - Staging API** (том, где работает echo):

1. В текущем staging Client ID уже включён в owner setup. Для другого клиента задайте **Настройки проекта → Свойства скрипта → GOOGLE_CLIENT_IDS**, затем **Сохранить свойства скрипта**. Несколько разрешённых клиентов можно перечислить через запятую.
2. После загрузки нового кода откройте редактор, выберите функцию **setupStagingAuth** и нажмите **Выполнить**.
3. Подтвердите запрошенные разрешения Google. Добавляется получение открытых ключей Google через внешнее HTTPS-соединение.
4. Ожидаемый журнал: `Staging auth настроен. Приглашений: 1.` Функция создаёт приглашение владельцу на 7 дней и проверяет доступность ключей Google. Повторный запуск сохраняет существующие приглашения и привязки.

Пустой проект, открытый через таблицу, здесь не используется. `setupStagingAuth` доступна только из редактора, публичного HTTP-действия для создания владельца нет.

## 3. Подключить сайт

Разработчик сохраняет публичный Client ID:

- в `apps/web/.env.staging.local` как `VITE_GOOGLE_CLIENT_ID`;
- в GitHub repository variable `STAGING_GOOGLE_CLIENT_ID`;
- публикует новую версию рабочего Apps Script deployment, сохраняя `/exec` URL;
- запускает workflow **Publish staging**.

Незаданный Client ID оставляет понятное сообщение «Вход Google ещё настраивается». Секрет OAuth-клиента не используется и не попадает в сборку. В production этот staging-проверяющий модуль выключен независимо от Client ID.

## 4. Проверить вход

1. Откройте [Tastory → Настройки](https://kaerna-group.github.io/tastory/#/settings).
2. В блоке **Ваш аккаунт** нажмите Google и выберите приглашённый аккаунт.
3. Ожидаются имя, email, роль и текст **Вход выполнен. Доступ подтверждён.**
4. Нажмите **Проверить доступ** — сервер заново проверит подпись токена и приглашение.
5. Нажмите **Выйти**. Повторный вход должен вернуть тот же аккаунт без второй привязки.
6. Проверьте другой, неприглашённый аккаунт: ожидается отказ без выдачи профиля Tastory.
7. Временно удалите приглашение тестового участника из `STAGING_INVITES`, затем нажмите **Проверить доступ** у него: ожидается отказ. После проверки восстановите приглашение при необходимости.

Не пересылайте ID token и не включайте запись сетевого трафика/Playwright trace при настоящем входе. В отчёт входят версия deployment, браузер, результат, время и requestId; без токенов и персональных данных.

## Пригласить тестового участника или отозвать доступ

На этапе spike владелец редактирует JSON в Script Property `STAGING_INVITES`. Максимум 10 записей:

```json
[
  {
    "email": "owner@gmail.com",
    "role": "owner",
    "expiresAt": "2026-09-10T12:00:00.000Z"
  },
  {
    "email": "reader@gmail.com",
    "role": "viewer",
    "expiresAt": "2026-09-10T12:00:00.000Z"
  }
]
```

Замените адреса и срок на актуальные; время указано в UTC. Разрешены роли `owner`, `member`, `viewer`. Срок ограничивает только первый вход. Для отзыва удалите запись из списка; пустой массив отключает доступ всем. Сам по себе role пока является атрибутом доступа: проверка прав на операции с рецептами появится вместе с такими операциями.

Сервер сохраняет потребление приглашения в отдельной `STAGING_AUTH_BINDINGS` одной записью под ScriptLock. **Не очищайте эту property для отзыва:** удалённое приглашение перестаёт давать доступ, а сохранённая привязка не позволяет передать его другому `sub`. Смена email в Google не меняет идентичность уже допущенного пользователя. Повторный допуск тому же `sub` возможен при восстановлении исходного приглашения.

Первый вход разрешён для Gmail и Google Workspace: для иных адресов Google не гарантирует текущее владение почтой, даже если `email_verified=true`. Их допуск потребует отдельного подтверждения. [Правила Google](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token).

## Контроль реализации и ограничения

- `auth.signIn` проверяет подписанный Google ID token, затем принимает приглашение. `auth.me` повторно проверяет токен и уже существующую привязку.
- Принимается только RS256. Ключи берутся с фиксированного HTTPS endpoint Google, кешируются на срок Cache-Control (не более 6 часов). Refresh ограничен по времени и защищён ScriptLock. JWT не выбирает endpoint ключей.
- Проверяются подпись, `iss`, `aud`, `azp` при наличии, `exp`, `iat`, `nbf` при наличии, `sub`, email и `email_verified`. Неожиданные поля заголовка/алгоритмы отклоняются. Токен ограничен 6144 символами, запрос — 8192.
- Токен хранится только в памяти вкладки до истечения срока/выхода. Перезагрузка требует повторного входа. Собственная refresh-сессия, cookies и хранение токенов в localStorage отсутствуют.
- Ответы ошибок не содержат токенов, внешних исключений или списка приглашённых. CORS не служит проверкой прав; cookies к Apps Script не отправляются.
- Schema version остаётся 0: временный реестр находится в Script Properties, не создаёт полную схему Sheets. Перед этапом 2 нужна явная миграция привязок без повторного захвата приглашений.
- Совместимый криптографический адаптер и отличие от предложения blueprint описаны в [ADR 0004](adr/0004-staging-google-auth.md). Решение для production ещё требует review.

Проверки: реальные RSA-подписи в unit tests и в собранном Apps Script IIFE без WebCrypto/Node/browser API; отрицательные claims/подписи; отказ чужому `sub`, отзыв, повторный вход; отмена/выход/истечение клиентской сессии. Эти проверки не заменяют вход с настоящим Google-аккаунтом и проверку нескольких браузеров. S0-04/S0-05 остаются открытыми до такого прогона.
