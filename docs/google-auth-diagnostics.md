# Диагностика ошибок входа

При `AUTH_UNAVAILABLE` после успешной `setupStagingAuth` не повторяйте редактирование приглашений и полный прогон отзыва. `setupStagingAuth` проверяет приглашения и доступность endpoint ключей, но не реестр привязок аккаунтов.

Функция загружена в редактор рабочего проекта 3 сентября 2026, `09:27:47.491Z` UTC; чтением Apps Script API подтверждены исходный код и сохранение manifest. Опубликованный `/exec` остаётся на версии 4. Свойства и привязки при загрузке не менялись.

## Полученный результат

Владелец выполнил диагностику в `2026-09-03T09:36:49.657Z`. [Отчёт](evidence/2026-09-03-auth-bindings-diagnostic.json) показал `bindings: invalid-schema`, поля `1.sub`, `1.joinedAt`, `1`. Индекс 1 обозначает **второй объект** массива `STAGING_AUTH_BINDINGS`. Приглашения (2), клиент, кэш ключей, получение ключей Google и блокировка прошли свои проверки.

Текущая серверная реализация преобразует ошибку разбора привязок в `AUTH_UNAVAILABLE`. Последующее значение, переданное владельцем, подтвердило причину: **второй объект оказался приглашением читателя** с `email`, `role`, `expiresAt`, без `sub` и `joinedAt`. Содержимое настоящей привязки владельца и Google ID в репозиторий не копируются.

## Исправить подтверждённую ошибку

1. Сохраните исходное значение `STAGING_AUTH_BINDINGS` у себя для восстановления.
2. Удалите из него только ошибочный второй объект приглашения читателя и разделяющую запятую. Сохраните внешние `[ ]` и первый объект владельца целиком, без изменения оригинальных email, sub и joinedAt. Не подставляйте вместо email владельца маску из переписки.
3. В `STAGING_INVITES` оставьте оба приглашения. Сохраните свойства и выполните `diagnoseStagingAuth`: для показанного владельцем состояния ожидаются `bindings: valid, count: 1` и `invitations: valid, count: 2`.
4. Начните новую запись проверки доступа и войдите читателем. Сервер сам создаст его правильную привязку после проверки Google token; вручную поля идентичности не вводите.
5. После успешного входа продолжите [отзыв и восстановление](google-access-staging.md#3-отзыв-у-тестового-участника-и-восстановление), меняя только `STAGING_INVITES`. Настоящую привязку читателя после её появления не удаляйте.

Точная инструкция с тестовым адресом — `.local/google-bindings-repair.md`, вне Git. Удаление ошибочного объекта проверено на синтетических данных через настоящую схему и политику проекта: owner сохраняется, Google-вход создаёт одну привязку viewer, повтор не дублирует её, отзыв и восстановление сохраняют идентичность. Это локальная проверка предложенной правки; **сохранение в Google и успешный вход ещё ожидаются**.

## Один запуск владельца

1. Обновите редактор рабочего **Tastory - Staging API**, куда загружена функция `diagnoseStagingAuth`.
2. Выберите в списке функций **diagnoseStagingAuth** и нажмите **Выполнить**.
3. Скопируйте JSON из журнала выполнения и передайте для разбора. Он содержит только статусы, количества записей, время и названия неверных полей.

Заново публиковать web app не нужно: функция запускается из редактора. Публичный `/exec` не принимает действие `diagnoseStagingAuth`. Токены, email, Google sub, значения свойств, содержимое ключей и тексты исключений в отчёт не выводятся.

## Что проверяется

| Поле               | Что означает                                                              |
| ------------------ | ------------------------------------------------------------------------- |
| `environment`      | Прочитан ли `APP_ENV` и равен ли он `staging`.                            |
| `clientIds`        | Есть ли список Google Client ID правильного формата.                      |
| `invitations`      | JSON и схема `STAGING_INVITES`; количество при успехе.                    |
| `bindings`         | JSON и схема `STAGING_AUTH_BINDINGS`; количество при успехе.              |
| `keyCache`         | Формат существующего кэша ключей Google.                                  |
| `keyRefreshMarker` | Присутствует ли ограничитель частоты обновления ключей.                   |
| `googleKeys`       | Получение и проверка схемы ключей с фиксированного HTTPS endpoint Google. |
| `scriptLock`       | Удалось ли получить и сразу освободить блокировку в течение 1 с.          |

`invalid-json` означает ошибку синтаксиса, `invalid-schema` — несоответствие ожидаемой структуре. Например, `bindings.fields: ["0.sub"]` указывает поле первой привязки, не раскрывая её содержимое. Чужие имена полей заменяются на `?`; количество и длина путей ограничены.

`keyCache: missing` может быть нормальным: API получает ключи заново. `bindings: missing` означает отсутствие property; обычный API в таком случае использует пустой массив. `keyRefreshMarker: present` сам по себе не является ошибкой. `scriptLock: busy` — наблюдение в момент диагностики, а не доказательство постоянного сбоя.

Функция не записывает и не удаляет свойства, привязки или кэш. Существующая политика допуска не меняется. Получение ключей использует разрешение внешних запросов, уже необходимое обычному входу. Диагностика выполняется от владельца в редакторе и не проверяет реальный token, запись новой привязки, соответствие email/sub или все условия доступа; общего флага «вход исправлен» нет.

После результата исправляем только установленную причину. До этого `STAGING_AUTH_BINDINGS` не очищаем и повторный захват приглашений не разрешаем.
