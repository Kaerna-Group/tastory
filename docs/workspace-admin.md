# Участники и состояние таблиц

Шаг D-02c: начало раздела владельца после [подтверждённого включения доступа через Sheets](evidence/2026-09-03-sheets-auth-activated.json). Просмотр участников и проверка структуры хранилища реализованы. Изменение ролей, приглашения, журнал операций и аудит — следующий шаг D-02d; весь этап 2 пока открыт.

## Как пользоваться

1. Открыть [настройки Tastory](https://kaerna-group.github.io/tastory/#/settings) и войти владельцем.
2. В разделе **Участники тетради** нажать **Показать участников**. Для каждого показаны имя или email, роль и состояние доступа.
3. Нажать **Проверить таблицы**. Успешный результат подтверждает структуру шести основных листов, применённую миграцию и корректный состав участников. Показаны число участников и число активных допусков.

Запросы выполняются по кнопке; каждый результат отмечен временем. При обновлении старый результат соответствующей проверки очищается. После выхода, истечения сессии, отказа в доступе или смены аккаунта список удаляется из интерфейса и памяти компонента. Читатель и обычный участник раздела не видят. Дополнительного запуска функций в Apps Script для этого шага нет.

## Серверные границы

- `admin.users.list` и `admin.health` требуют проверенный Google ID token и активного владельца выбранной книги. Payload строго пустой: передать роль, email, UUID пользователя или другой workspace нельзя.
- После проверки JWT сервер повторно читает каталог под ScriptLock и проверяет владельца по `Users.google_sub` и членству именно этой книги. Роль из более ранней сессии сама по себе не даёт разрешения. Срок токена проверяется после ожидания блокировки и перед возвратом данных.
- Список содержит только участников выбранной книги. Возвращаются внутренние UUID, отображаемые email/имя, роль, статусы аккаунта и членства, время вступления. Google sub, нормализованные адреса, Script Properties, ID таблицы и Drive не возвращаются.
- `admin.health` повторно применяет существующий план проверки схемы без записи: шесть заголовков, Meta, версия, контрольная сумма и журнал миграции. Состав Users/Workspaces/WorkspaceMembers также проходит проверки схемы и связей. Строки Invites, приватные файлы, квоты и восстановление резервной копии этим результатом не проверяются.
- Операции только читают. Нет создания листов, изменения ролей, погашения приглашений, записи профилей или отправки писем. Повторы чтения не требуют журнала идемпотентности.
- Если каталог доступа повреждён или включён maintenance, проверка недоступна: административный endpoint не обходит авторизацию. Сбои скрывают внутренние исключения. Прежний реестр Script Properties не используется как запасной источник доступа.

Публичный `health` остаётся лёгкой проверкой доступности API без приватных данных. Проверка таблиц доступна через авторизованный `admin.health`. Формат envelope API v1 и транспортный `meta.schemaVersion: 0` сохранены, фактическая схема таблиц — 1.

## Проверки и следующий шаг

Автотесты проверяют ограничение по книге, отказ member/viewer, изменение/отзыв роли между авторизацией и чтением, истечение токена, ошибки схемы и отсутствие записи. Собранный Apps Script проверяется с настоящей подписью синтетического JWT. Браузерные fixtures проверяют показ ролей/отключённого доступа, мобильную ширину, ошибку обновления, выход и скрытие раздела для читателя. Они не выдают себя за вход реальных Google-аккаунтов.

Следующий шаг: журнал операций и AuditLog, затем создание/отзыв приглашений и изменение членств с ревизиями, повторяемым применением и серверной защитой владельца. Новые пользователи смогут вступать после реализации этого пути записи.
