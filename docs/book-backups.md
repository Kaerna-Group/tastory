# Резервная копия и восстановление книги — минимум O-02

Реализовано и проверено в изолированной среде 3 сентября 2026. Рабочий Google-проект этой задачей не обновлялся. До хранения ценных рецептов необходимо выполнить описанную ниже проверку на настоящем Google Drive.

## Действия владельца

После публикации совместимого backend и web, с подготовленной схемой 3:

1. Открыть **Настройки → Резервные копии** и нажать **Создать резервную копию**. При первом запуске создаётся отдельная приватная папка резервных копий; её ID записывается в Script Property `BACKUP_FOLDER_ID`. Можно заранее указать свою приватную папку вне папки файлов книги.
2. При потере соединения повторить действие. Браузер сохраняет ID запроса до отправки, отдельно для аккаунта, API и действия. После перезагрузки войти тем же аккаунтом. Через **Открыть копии** также можно продолжить сохранённый незавершённый план.
3. Нажать **Проверить копию**. Проверяются контрольные суммы таблиц, наличие всех файлов, их размеры, типы, SHA-256 и приватность.
4. Нажать **Восстановить отдельно**. Открыть полученные ссылки на новую таблицу и папку; проверить рецепты, ингредиенты, шаги, теги, историю и роли. Приложение продолжает использовать прежнюю книгу.
5. После проверки администратор останавливает входящий трафик старого развёртывания и переносит значения из приватного `configuration.json` в Script Properties. Файл содержит новые `SPREADSHEET_ID`, `DRIVE_FOLDER_ID`, конфигурацию входа и переназначенные ссылки диагностического фото. Затем проверить вход владельца/читателя и создать новое развёртывание. Нельзя переключать два ID по очереди при работающем трафике.

Автоматическое переключение и восстановление поверх текущих данных не выполняются. Повтор восстановления с тем же ID продолжает те же отдельные ресурсы. После завершения повтор проверяет их без перезаписи; внесённые после восстановления изменения не затираются.

## Что входит в копию

- Все непустые листы книги, включая 14 таблиц схемы 3, системные метаданные, миграции, Users/Workspaces/WorkspaceMembers, приглашения, журнал доступа и рабочие квитанции рецептов. Значения сохраняются как текст, как и в прикладном хранилище. Оформление таблицы и Google-формулы не экспортируются; формулы приводят к отказу проверки.
- Все обычные файлы и вложенные папки из `DRIVE_FOLDER_ID`, включая JPEG и неизменяемые файлы архива истории. Сохраняются имена, структура, MIME, размеры и SHA-256. Копируются и проверяются именно байты; приватные файлы не публикуются.
- Только разрешённые настройки: `APP_ENV`, `SHEETS_AUTH_CONFIG`, `GOOGLE_CLIENT_IDS`, `STAGING_PHOTO_<hash>`. OAuth-токены, credential, настройки clasp и прочие Script Properties в экспорт не попадают. Пользовательские заметки, email и права входят в приватные данные книги.

Во время создания снимка сервер удерживает ту же ScriptLock, что и записи приложения. Перед копированием проверяются схема, каталог участников, цепочка квитанций и сохранённые снимки рецептов. Незавершённые операции рецептов или доступа требуют сначала завершения/отмены: API вернёт `BACKUP_PENDING`.

План копии сохраняется до переноса файлов. Каждый файл копируется с повторной проверкой, а маркер готовности содержит hash всего плана и публикуется последним. Прерванный план не показывается готовым. Если ещё не скопированный исходный файл изменился/исчез, старый план не подменяется: нужен новый ID копии. UI продолжает использовать прежний ID до успеха; для такого случая оператор запускает новый create-запрос с новым UUID. Автоматическое удаление незавершённых планов не выполняется.

При восстановлении строки таблиц записываются порциями с проверкой уже сохранённых частей. Меняется только ссылка `Meta.drive_root_folder_id` на новую папку. UUID пользователей, книги, рецептов, связей, ревизии и requestId сохраняются. Ссылки на реальные файлы фото переназначаются через карту old→new ID. Архив использует имена по содержимому и поэтому не зависит от прежних Drive ID. В конце заново проверяются восстановленные таблицы, модель и архив.

## Авария исходной книги

Если исходная таблица исчезла или повреждённый каталог не позволяет войти в приложение, владелец приватной папки запускает из редактора Apps Script функцию `recoverBookBackup`:

1. Сохранить `BACKUP_FOLDER_ID` и UUID нужной копии отдельно от основной книги.
2. В Script Properties указать `BACKUP_RECOVERY_ID`. При первом запуске функция сохранит `BACKUP_RECOVERY_REQUEST_ID`; не менять его при повторе того же восстановления.
3. Запустить `recoverBookBackup`. Функция читает только запечатанную копию, проверяет владение приватной папкой и возвращает ссылки на восстановленные ресурсы. Исходная таблица и её файлы могут отсутствовать полностью.
4. Для другого восстановления задать другой `BACKUP_RECOVERY_ID` и новый UUID `BACKUP_RECOVERY_REQUEST_ID`. Проверить книгу и переключить конфигурацию по процедуре выше.

Этот операторский вход отсутствует в HTTP allowlist. Резервная папка в том же Google-аккаунте не защищает от потери всего аккаунта; независимый экспорт за его пределы и расписание копирования остаются расширением O-02.

## API и пределы

Все HTTP-действия доступны только действующему владельцу по текущему каталогу и живой Google-сессии:

| Действие                | Payload        | Результат                                                 |
| ----------------------- | -------------- | --------------------------------------------------------- |
| `admin.backups.list`    | `{}`           | Последние 100 готовых копий и до 100 незавершённых планов |
| `admin.backups.create`  | `{}`           | Готовая копия; повтор использует прежний requestId        |
| `admin.backups.verify`  | `{ backupId }` | Копия после проверки целостности                          |
| `admin.backups.restore` | `{ backupId }` | Ссылки на отдельные восстановленные ресурсы               |

Защитные пределы: до 50 листов, 100 001 строки и 100 колонок на лист, 100 вложенных папок, 2000 файлов, 20 MiB на файл, 200 MiB суммарных файлов. JSON плана при чтении ограничен 50 MiB. Нативные Google Docs/Sheets/shortcuts внутри папки файлов и одинаковые имена в одной папке отклоняются. Это технические верхние границы, а не подтверждённая производительность на Google. Для значительных объёмов нужны O-03: реальные замеры квот, времени и дальнейшее разбиение работ. Ручное редактирование ресурсов Google вне приложения не контролируется ScriptLock.

`BACKUP_INVALID` означает нарушение целостности/несовместимый план, `BACKUP_PENDING` — незавершённую запись книги, `BACKUP_LIMIT` — превышение границ, `BACKUP_UNAVAILABLE` — неподтверждённый результат, который можно повторить с прежним ID.

## Подтверждения

Unit/integration-проверки создают книгу с рецептом, историей и файлами, моделируют сбой до и после каждого шага копирования/восстановления, потерю исходных ресурсов, повреждения, чужую роль, истечение сессии, сохранение прав и переназначение ссылок. Браузерные проверки desktop/mobile покрывают потерю ответа, перезагрузку, прежний ID, проверку и ссылки на отдельное восстановление. Изолированные тесты не заменяют запуск настоящей копии и восстановления владельцем после публикации.

Копирование файлов использует [официальный Drive File API](https://developers.google.com/apps-script/reference/drive/file).
