# Журнал операций и аудит

Шаг D-02d-01: основа сохранения операций и восстановления после потери ответа. В настройках владельца появился **Журнал операций**. Сейчас зарегистрировано одно действие — проверка самого журнала. Приглашения, изменение ролей и рецепты будут подключаться отдельными задачами; весь D-02 пока открыт.

Сервер опубликован в версии **7** 3 сентября в 12:53:30 UTC из `d9441f7`. Исходники редактора и снимок версии проверены, URL и manifest сохранены. [Проверки выпуска](evidence/2026-09-03-operation-journal-release.json). Подготовка двух новых листов в настоящей Google-таблице и положительный прогон владельца пока ожидаются.

## Действия владельца

1. Обновить [настройки Tastory](https://kaerna-group.github.io/tastory/#/settings), войти владельцем.
2. В разделе **Журнал операций** нажать **Открыть журнал**, затем **Подготовить журнал**. Создаются `Operations` и `AuditLog`, применяется миграция 002. Повтор подготовки безопасен.
3. Нажать **Проверить сохранение и повтор**. Два запроса с одним ключом должны оставить одну завершённую операцию и одно событие аудита. Ожидается сообщение **Проверка пройдена: запись и аудит сохранены, повтор не создал дубликат.**
4. При потере ответа нажать **Повторить ту же проверку**. После перезагрузки снова войти, открыть журнал и у незавершённой записи нажать **Завершить проверку**. Продолжить её может тот же действующий владелец.

Google-редактор для этих действий не нужен. Доступ через Sheets уже включён; повторять импорт и активацию не нужно. После перехода на схему 2 не запускайте старые `setupStagingSchema` и `setupStagingUsers`: это инструменты первого развёртывания схемы 1.

## Сохранение и повтор

Все действия журнала требуют Google ID token и активного владельца. Под общей ScriptLock сервер заново читает каталог, проверяет членство именно выбранной книги и срок токена. Проверка срока повторяется перед записью и ответом. Поля роли, книги и пользователя из клиента не принимаются.

Ключ операции — `requestId`. SHA-256 связывает его с версией формата, действием, внутренним UUID пользователя, книгой и каноническим пустым payload. Изменение этой привязки даёт `OPERATION_MISMATCH`.

Проверка журнала выполняет последовательность:

1. Записать `Operations` со статусом `started`, сбросить изменения и прочитать их обратно.
2. Добавить единственное событие `AuditLog` с `event_id = request_id`, сбросить и проверить.
3. Сохранить статус `committed`, время и фиксированный результат проверки, сбросить и проверить.

Каждый шаг проверяет уже сохранённое состояние. Потеря ответа или прерывание между шагами не создают вторую операцию или событие. Завершённая операция возвращает прежний результат без записи, в том числе после более новой операции. Неопределённый исход не помечается как окончательный отказ: запись остаётся доступной для продолжения.

Это явно реализованный переход для `admin.operations.check`, а не универсальный повтор произвольного обработчика. Проверка не меняет продуктовые данные и `Meta.data_revision`. Для приглашений и CRUD потребуется собственный восстанавливаемый переход с проверкой ожидаемой ревизии.

## Схема 2 и совместимость

Миграция `002-operation-journal` добавляет два листа. Состав и контрольная сумма миграции `001-core-schema` сохранены. Проверка схемы 2 исключает только известную и предварительно проверенную запись 002 из представления для исходного валидатора; неизвестные миграции, изменённые заголовки и контрольные суммы отклоняются.

После создания заголовков записывается маркер миграции, затем последним обновляется `Meta.schema_version`. Подготовку можно продолжить после прерывания на каждом шаге. Данные существующих пользователей и членств не перезаписываются. Пока миграция не завершена, проверка структуры старого раздела может временно отвечать ошибкой; повтор **Подготовить журнал** завершает переход.

Вход через Sheets поддерживает версии 1 и 2. `admin.health` показывает соответственно 6 или 8 проверенных таблиц; он проверяет структуру, а не все строки журнала. API v1 и транспортный `meta.schemaVersion: 0` сохранены. Подготовка учитывается в `SchemaMigrations`, а не как операция `admin.operations.check`.

## Границы и данные

- `Operations`: ключ запроса, книга, внутренний пользователь, действие и сущность, hash payload, статус, результат, код ошибки, начало и завершение. Дополнительный к blueprint `workspace_id` позволяет ограничить видимость незавершённых записей книгой.
- `AuditLog`: уникальный event/request ID, книга, пользователь, сущность, действие, before/after hash, metadata, время. Для проверки журнала before/after пустые, metadata содержит только вид проверки.
- Google sub, токены, email и ID ресурсов Google в новые листы не записываются. Имя автора для интерфейса читается из `Users`; при отсутствии имени используется email. API журнала не возвращает hashes, сырой результат хранения или Google ID.
- Не более 1000 операций и 1000 событий. Старые квитанции не удаляются по TTL: иначе повтор мог бы выполниться заново. При исчерпании лимита новая запись отклоняется; политика хранения будет отдельным шагом.
- Интерфейс показывает последние 50 операций текущей книги, без пагинации. Кнопка продолжения доступна для показанных незавершённых проверок текущего владельца.
- Строгие заголовки, размеры, формулы, повторные ID, сиротские события и несовместимое состояние проверяются перед работой. При повреждении журнал недоступен; автоматического удаления или исправления чужих строк нет.
- Чтение списка не создаёт записей. Существующие диагностические photo/concurrency действия и прошлые события не переносятся в новый аудит. Изменение приглашений и членств ещё не реализовано.

## Подтверждения

Локальные тесты моделируют сбои до и после каждого шага миграции и записи, повтор после новых операций, несовпадение привязки, отзыв роли, истечение сессии, повреждение/переполнение таблиц и отсутствие лишних записей. Собранный Apps Script проверен с тестовым RSA JWT, включая сохранение входа owner/viewer после миграции и health восьми таблиц.

Браузерные fixtures проверяют подготовку, единственный результат после повтора, потерю ответа, продолжение после перезагрузки, скрытие для читателя и мобильную ширину. Они не заменяют положительную проверку владельца на настоящей Google-таблице.
