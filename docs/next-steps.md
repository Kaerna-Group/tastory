# Что делать дальше

План после публикации основы проекта, 2 сентября 2026 года. Подробные критерии — в [roadmap](roadmap.md) и [чек-листе платформы](spike-checklist.md).

## 1. Подключить тестовое окружение Google

Apps Script project уже создан, код загружен. Следующий шаг — запуск владельцем `setupStaging`, который создаст отдельные тестовые Spreadsheet и папку Google Drive. Пошаговая [инструкция](google-staging.md).

Со стороны владельца потребуется вход в Google и подтверждение разрешений Sheets/Drive в редакторе Apps Script. Clasp уже подключён. Для следующего шага понадобится опубликованный URL `/exec`; приватный ключ или пароль передавать в переписку не нужно.

Порядок работы:

1. Запустить `setupStaging` и проверить ссылки на созданные таблицу и папку.
2. Зафиксировать результат создания в чек-листе платформы.
3. Создать тестовый web app deployment по [инструкции](apps-script.md#публикация-staging-web-app).
4. Подставить его URL в локальную конфигурацию staging.
5. Проверить реальный ответ API из приложения.
6. Опубликовать тестовую web-сборку на согласованном staging-адресе и повторить запросы с этого origin.

**Результат:** React читает JSON-ответ Apps Script после redirect с реального домена. Наличие ответа в адресной строке браузера само по себе этот сценарий не подтверждает.

## 2. Проверить вход Google и приглашения

- Настроить OAuth web client и разрешённые origins для выбранных адресов.
- Добавить вход Google и серверную проверку подписи, issuer, audience и срока ID token.
- Привязать пользователя к проверенному `sub`, проверить допуск по приглашению.
- Проверить отказ для чужого пользователя, поддельного и истёкшего токена.

**Результат:** сервер устанавливает личность пользователя самостоятельно и разрешает доступ только приглашённым. Полная модель ролей и администрирование будут на этапе 2.

## 3. Доказать работу фотографий и конкурентных записей

- Оптимизировать тестовое фото в браузере и загрузить в приватную папку Drive.
- Получить миниатюру через API с проверкой прав; проверить отказ без доступа.
- Выполнить две конкурентные записи с LockService и ревизиями на тестовых данных.
- Измерить задержки и размеры запросов; выбрать загрузку целым файлом или частями.
- Записать результаты и решение в checklist/ADR.

**Результат:** закрыт критический gate этапа 0. Если CORS, auth или приватная выдача нестабильны, сначала пересматриваем серверную часть.

## 4. Реализовать схему данных и пользователей

После gate платформы:

- Объявить схему листов и создать setup/migrations с Meta и версией схемы.
- Реализовать Users, Invites, Workspaces и Members.
- Добавить роли owner/member/viewer и серверные проверки доступа.
- Добавить журнал операций, идемпотентность запросов и аудит.
- Расширить health настоящими проверками хранилища.

**Результат:** владелец приглашает участников, viewer не может записывать данные, миграции можно повторять без повреждения таблиц.

## 5. Сделать первый полноценный рецепт

- Название, описание, главное фото, порции и время.
- Ингредиенты, шаги, теги и заметки.
- Создание, изменение, просмотр, архивирование и восстановление.
- Библиотека, поиск, фильтры и избранное.
- Локальный черновик, автосохранение и понятный конфликт версий.
- Удобный сценарий на телефоне.

**Результат:** рецепты можно вести ежедневно без дизайнерского режима.

## 6. Развивать оформление и готовить релиз

Дальнейший порядок из blueprint: страницы и шаблоны → ограниченный редактор → стикеры и темы → импорт/экспорт, версии и резервные копии → PWA и релиз MVP.

Каждая часть добавляется поверх работающего структурированного рецепта. Мобильные и desktop-оболочки остаются после MVP.
