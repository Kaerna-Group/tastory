# Базовая схема и миграции

Первый шаг этапа 2, задача D-01, 3 сентября 2026 года. Основание: [blueprint, раздел 16.2](../recipe-book-project-blueprint.md#162-вкладки-первой-очереди).

Код создаёт шесть листов в уже настроенной staging-таблице, заполняет `Meta` и регистрирует миграцию `001-core-schema`. Пользовательские листы получают только заголовки: перенос пользователей и приглашений будет отдельным шагом. Настоящее выполнение в Google подтверждается результатом запуска владельца; локальные тесты его не заменяют.

Функции загружены в редактор рабочего проекта 3 сентября в 10:20:45 UTC, исходный код проверен повторным чтением. Владелец затем прислал три настоящих результата: план, `applied` и `already-applied`. В последнем запуске версия 1, все шесть действий `keep`. **D-01 выполнен.** [Сохранённые отчёты](evidence/2026-09-03-core-schema-applied.json). На момент завершения D-01 API был версии 4; последующий выпуск 5 описан в [подключении входа к таблицам](sheets-auth-staging.md).

## Запуск владельцем

В текущем staging эти действия уже выполнены и подтверждены. Инструкция сохранена для повторяемости; следующий шаг — [перенос пользователей](users-import-staging.md).

1. Открыть **Tastory - Staging API**, рабочий отдельный проект Apps Script, и обновить страницу редактора. Использовать тот же проект, где запускалась `diagnoseStagingAuth`.
2. Выбрать функцию **planStagingSchema** и нажать **Run / Выполнить**. Она только проверяет таблицу. При `ok: true` в журнале появится план для шести листов с действиями `create`, `initialize` или `keep`.
3. Если план успешен, выбрать **setupStagingSchema** и выполнить. Ожидаемый результат: `ok: true`, `result: "applied"`, `toVersion: 1`.
4. Выполнить **setupStagingSchema** ещё раз. Ожидается `result: "already-applied"`. Новых листов и записей в журнале миграций не появится.
5. Прислать JSON из журнала второго запуска. Он содержит только результат и названия листов, без адресов, Google ID и ID таблицы.

Используются существующие свойства `APP_ENV=staging`, `SPREADSHEET_ID` и `DRIVE_FOLDER_ID`. Новые таблица и папка не создаются. Если Google запросит доступ к текущей таблице при запуске, подтвердить его своим аккаунтом владельца проекта. Публиковать новую версию web app для запуска этих функций не требуется.

При `ok: false` сохранить код ошибки и остановиться. Не удалять листы, журнал миграций или свойства входа, чтобы добиться успешного результата.

## Листы

| Лист             | Назначение                                 | Столбцы в установленном порядке                                                                                              |
| ---------------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Meta             | Версии и настройки хранилища               | key, value, updated_at                                                                                                       |
| SchemaMigrations | История миграций                           | migration_id, name, checksum, applied_at, applied_by, status                                                                 |
| Users            | Будущие серверные учётные записи           | user_id, google_sub, email, email_normalized, display_name, avatar_asset_id, status, created_at, last_login_at, row_revision |
| Invites          | Будущие приглашения в рабочие пространства | invite_id, workspace_id, email_normalized, role, invited_by, expires_at, used_by, used_at, status                            |
| Workspaces       | Кулинарные книги и их владельцы            | workspace_id, name, owner_user_id, default_app_theme_id, default_canvas_theme_id, created_at, updated_at, row_revision       |
| WorkspaceMembers | Участие и роль в конкретной книге          | workspace_id, user_id, role, status, joined_at, row_revision                                                                 |

`Members` в кратком backlog означает `WorkspaceMembers` из blueprint. Состав столбцов определён в `apps/apps-script/src/schema/core-schema.ts`; файлы с пользовательскими данными в репозиторий не добавляются.

### Meta после успешного первого запуска

| Ключ                 | Значение                                      |
| -------------------- | --------------------------------------------- |
| schema_version       | 1                                             |
| api_version          | 1                                             |
| data_revision        | 0, если значение ещё не существовало          |
| created_at           | Время первого заполнения, UTC ISO 8601        |
| drive_root_folder_id | ID уже настроенной папки из Script Properties |
| maintenance_mode     | false, если значение ещё не существовало      |

`updated_at` хранит время записи в UTC. Существующие корректные значения и дополнительные ключи сохраняются. Другая папка или версия API считаются конфликтом конфигурации.

Версия **схемы хранилища 1** пока отделена от метаданных старого диагностического API: опубликованная версия web app 4 продолжает сообщать `schemaVersion: 0`. Подключение основного API к таблицам и смена его контрактов будут отдельной миграцией приложения; создание заголовков ещё не означает перенос данных или готовую авторизацию на Sheets.

## Порядок и защита данных

- Весь запуск защищён общей `ScriptLock`. Сначала проверяются все шесть листов, затем разрешается запись.
- Отсутствующий лист создаётся, пустой получает заголовки. У существующего листа проверяются точные имена и порядок столбцов. Посторонние листы сохраняются.
- В `Users`, `Invites`, `Workspaces`, `WorkspaceMembers` читается только первая строка. Миграция не загружает и не меняет строки с пользовательскими данными.
- У `Meta` и `SchemaMigrations` проверяются строки, уникальность ключей и отсутствие формул. Чтение ограничено 1000 строками на системный лист. Дополнительный заполненный столбец или формула останавливают настройку.
- Все записываемые значения имеют текстовый формат. Формулы запрещены: Google Sheets интерпретирует строку с начальным `=` как формулу. Используемые методы чтения/записи описаны в [официальной документации Range](https://developers.google.com/apps-script/reference/spreadsheet/range).
- Сначала записываются заголовки и недостающие настройки, затем строка миграции `applied` и `flush`, последним — `schema_version=1` и ещё один `flush`. После записи схема читается и проверяется повторно.
- При ошибке до фиксации версии миграция по возможности получает `failed`. Частично созданные листы не удаляются; повтор продолжает настройку с сохранённого состояния. Если ответ потерялся после фиксации версии, успешная запись журнала сохраняется.
- Контрольная сумма SHA-256 включает идентификатор, заголовки, ключи и версию алгоритма миграции. После выпуска определение `001-core-schema` не изменяют: дальнейшие изменения требуют новой миграции.
- В `applied_by` записывается `system:setupStagingSchema`: это имя процедуры, а не подтверждённая личность запускающего. Полный аудит пользователей относится к D-02.

Это восстановление после прерывания, а не общая транзакция Sheets. Ручное изменение таблицы одновременно с настройкой не защищено `ScriptLock`; на время запуска не редактировать её содержимое.

## Ошибки

| Код                                                   | Действие                                                                                  |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| SCHEMA_BUSY                                           | Дождаться завершения другого запуска и повторить                                          |
| STAGING_REQUIRED / STORAGE_NOT_CONFIGURED             | Проверить рабочий проект и три свойства настройки                                         |
| HEADER_CONFLICT / FORMULA_IN_SCHEMA                   | Проверить указанный лист; не перезаписывать данные автоматически                          |
| INVALID_SYSTEM_ROWS / META_CONFLICT                   | Разобрать повреждённую или дублирующую запись в системном листе                           |
| NEWER_SCHEMA / MIGRATION_CONFLICT / UNKNOWN_MIGRATION | Сопоставить загруженный код с версией и журналом таблицы                                  |
| SCHEMA_DRIFT                                          | Схема с зафиксированной версией неполна; требуется разбор, а не повторное создание листов |
| SYSTEM_TABLE_TOO_LARGE                                | Проверить системный лист; превышен предел безопасного чтения                              |
| SCHEMA_WRITE_FAILED / SCHEMA_SERVICE_UNAVAILABLE      | Сохранить отчёт; после устранения причины повторить план                                  |

Функции доступны только из редактора проекта. Через HTTP действия с такими именами отклоняются. Свойства `STAGING_INVITES` и `STAGING_AUTH_BINDINGS` эта миграция не читает и не меняет; текущий Google-вход продолжает работать на прежнем реестре.

## Проверка и следующий шаг

Автотесты проверяют предварительный просмотр без записей, повтор без изменений, сохранность существующих данных, сбой до и после каждой операции записи/flush, несовместимые заголовки, версии, журнал и дубликаты. Отдельно проверены адаптер Sheets, блокировки, безопасный отчёт и собранные глобальные функции без Node/browser API, включая отказ публичного HTTP-вызова.

Настоящий повторный запуск подтверждён, D-01 закрыт 3 сентября. Начат D-02: подготовлен [перенос текущих привязок и приглашений](users-import-staging.md) с сохранением владельца. После его проверки предстоят подключение серверного входа к таблицам, роли и управление участниками.
