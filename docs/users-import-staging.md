## Действия владельца

В текущем staging перенос и повтор уже подтверждены. Эти действия сохранены для повторяемости; повторять перенос перед переключением входа не требуется.

1. Обновить редактор **Tastory - Staging API**, в котором только что выполнялась `setupStagingSchema`.
2. Выполнить **planStagingUsers**. Ожидается `ok: true`, количество пользователей, приглашений, участников и одна роль owner. Это предварительный просмотр без записи.
3. При успешном плане выполнить **setupStagingUsers**. Ожидается `result: "applied"` и `pendingRows: 0`.
4. Повторить **setupStagingUsers**. Ожидается `result: "already-applied"` и `pendingRows: 0`. Прислать JSON этого запуска.

При `ok: false` сохранить отчёт и остановиться. На время переноса не менять приглашения/привязки и не редактировать таблицу вручную. Если выполнение прервалось, сначала повторить план. Редакторские функции уже используют текущую таблицу: создавать ресурсы, вводить Google ID вручную или публиковать новую версию web app не требуется.

## Как переносятся записи

| Источник                               | Запись в таблице                                                             |
| -------------------------------------- | ---------------------------------------------------------------------------- |
| Каждая существующая привязка email/sub | Users: новый внутренний UUID, прежний google_sub и адрес                     |
| Единственный вступивший owner          | Workspaces.owner_user_id и активная роль owner в WorkspaceMembers            |
| Приглашение с существующей привязкой   | Invites со статусом used и участник с прежней ролью                          |
| Приглашение без привязки               | pending, либо expired, если срок уже прошёл; пользователя и членства ещё нет |
| Привязка без действующего приглашения  | Users сохраняет личность, членство не создаётся; доступ не восстанавливается |

Для уже вступившего участника срок первоначального приглашения не отменяет членство: это соответствует прежнему реестру. Владелец определяется из единственного приглашения owner и существующей привязки. Запускающий редактор должен иметь тот же email; при неоднозначном владельце перенос останавливается.

Внутренние UUID пользователей отличаются от Google `sub`. У созданных строк начальная `row_revision=1`. `created_at` пользователя и время вступления берутся из существующей привязки. Последний вход, имя профиля, аватар и темы не выдумываются: неизвестные поля остаются пустыми. Новые приглашения не отправляются, письма функция не рассылает.

## Повторы и ошибки

Предварительная проверка требует завершённую схему 1, правильные заголовки, `maintenance_mode=false`, корректные исходные массивы и не более 10 привязок/приглашений. Если начальный перенос ещё не зарегистрирован, четыре целевых листа должны быть пустыми. Посторонние существующие записи автоматически не принимаются и не перезаписываются.

Перед первой записью пользователей в Meta сохраняется техническая запись `users_import_v1`: версия алгоритма, UUID, время, исходная ревизия, SHA-256 нормализованного исходного реестра и статус prepared. Адреса и Google sub в этой записи не дублируются. По этим данным и неизменному реестру можно восстановить тот же план после прерывания.

Сначала добавляются пользователи, затем рабочее пространство, членство и приглашения. Существующие строки должны точно совпадать с планом. После проверки всех строк фиксируется `data_revision` на единицу больше исходной и состояние applied. Повтор не пишет строки и не повышает ревизию снова. Структура листов остаётся версией 1; это перенос данных, поэтому новая запись структурной миграции в SchemaMigrations не добавляется.

| Код                                                                        | Причина и следующий шаг                                                              |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| IMPORT_BUSY                                                                | Другой запуск держит блокировку; повторить позже                                     |
| IMPORT_STAGING_REQUIRED / IMPORT_SCHEMA_REQUIRED                           | Проверить рабочий проект, свойства ресурсов, схему и режим обслуживания              |
| IMPORT_OWNER_REQUIRED                                                      | Нужен единственный уже вступивший owner и запуск с его аккаунта                      |
| IMPORT_SOURCE_INVALID                                                      | Повреждён формат приглашений/привязок либо дублируются личности                      |
| IMPORT_SOURCE_CHANGED                                                      | Реестр изменился после начала переноса; нужен разбор, не очистка контрольной записи  |
| IMPORT_TARGET_NOT_EMPTY / IMPORT_TARGET_CONFLICT                           | Посторонние, изменённые, дублирующиеся или пропавшие строки                          |
| IMPORT_CHECKPOINT_INVALID / IMPORT_META_INVALID / IMPORT_REVISION_CONFLICT | Повреждена контрольная запись или изменилась ревизия; остановиться для разбора       |
| IMPORT_UNSAFE_VALUE                                                        | Обнаружены формулы или значения с префиксом формулы; автоматическая запись запрещена |
| IMPORT_CONFIG_INVALID                                                      | Не удалось получить допустимые уникальные UUID или параметры переноса                |
| IMPORT_WRITE_FAILED / IMPORT_UNAVAILABLE / IMPORT_VERIFY_FAILED            | Сохранить результат; после устранения причины повторить предварительный просмотр     |

Блокировка общая с текущим входом. Она защищает вызовы приложения, но не ручное редактирование Google Sheets. Прерывание восстанавливается продолжением; удаления и автоматического отката строк нет. После дальнейшего изменения приглашений или данных этот одноразовый перенос не используется как синхронизация.

Чтение ограничено 10 строками данных на целевой лист. Формулы обнаруживаются через `getFormulas`, данные читаются через `getValues`; [документация Range](https://developers.google.com/apps-script/reference/spreadsheet/range). UUID и контрольная сумма создаются средствами [Utilities](https://developers.google.com/apps-script/reference/utilities/utilities).

## Границы и проверка

Отчёт содержит только количества, роли, статус и безопасный код ошибки. Адреса, UUID, Google sub, исходные свойства и контрольная сумма не выводятся. Публичные HTTP-вызовы этих функций запрещены.

Автотесты проверяют сохранность идентичности и ролей, запрет повторного допуска отозванных участников, истёкшие/неиспользованные приглашения, сбой до/после каждой записи и flush, восстановление UUID, конфликты и отсутствие повторных изменений. Сборка дополнительно выполняет весь путь schema → users plan/apply/repeat в изолированной среде Apps Script.

После подтверждения результата следующий шаг — серверная работа с Users/WorkspaceMembers, проверка роли для каждого действия и управление участниками. Переключение работающего входа на Sheets проводится отдельно после сравнения перенесённых данных.
