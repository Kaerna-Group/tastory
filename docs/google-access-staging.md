# Проверка приглашений и отзыва доступа

Подготовлено 3 сентября 2026 года. В [настройках Tastory](https://kaerna-group.github.io/tastory/#/settings), внутри блока **Ваш аккаунт**, появился раскрывающийся раздел **Проверка приглашений**. Он записывает ответы настоящих `auth.signIn` и `auth.me`, явный выход и время запросов. Запись включается вручную; скачивание завершает её.

Инструмент подготовлен для оставшихся S0-04/S0-05. Автоматические сценарии с подставным провайдером проверяют сам инструмент; реальными результатами Google они не считаются. Первый вход владельца, фото и конкурентные записи уже подтверждены отдельно.

**Повторный вход владельца подтверждён 3 сентября:** [отчёт](evidence/2026-09-03-access-owner-repeat.json) содержит успешный вход, выход, второй вход того же `account-1` с ролью `owner` и успешный `auth.me`. `repeatedSignIn: true` соответствует событиям. Первый [частичный отчёт](evidence/2026-09-03-access-owner-partial.json) сохранён как история; повторять сценарий владельцу в этом браузере не требуется. [Подробности результата](staging-verification.md#повторный-вход-владельца).

**Отказ при входе подтверждён отдельным [отчётом](evidence/2026-09-03-access-denied.json):** `auth.signIn` вернул `ACCESS_DENIED` за 2921 мс. Файл передан в ответ на инструкцию входа вторым аккаунтом без приглашения; выбранная почта и список приглашений в отчёте отсутствуют. [Границы подтверждения](staging-verification.md#отказ-при-входе-вторым-аккаунтом). Следующий шаг — раздел 3: временное приглашение `viewer`, отзыв и восстановление.

Email второго аккаунта получен. Подготовлены локальные `.local/google-viewer-invitation.json` и `.local/google-viewer-access-check.md` с записью приглашения и точными шагами. Адрес исключён из Git. Редактор рабочего Apps Script требует входа владельца в доступном браузере, а подключение clasp не предоставляет изменение Script Properties. Запись ограничивает срок первого входа; для отзыва после принятия нужно удалить приглашение.

**Текущий результат:** владелец подтвердил, что во второй объект `STAGING_AUTH_BINDINGS` ошибочно записано приглашение читателя (`email`, `role`, `expiresAt`). [Точечное исправление](google-auth-diagnostics.md#исправить-подтверждённую-ошибку): удалить только этот объект, сохранив исходную привязку владельца и оба `STAGING_INVITES`, затем подтвердить диагностику и войти читателем. Правильную новую привязку создаёт сам сервер. Исправление в Google и успешный вход ещё не подтверждены; отзыв продолжить после них. [История проверки](staging-verification.md#ошибки-при-проверке-читателя).

## 1. Повторный вход владельца

1. Обновите опубликованные настройки и войдите владельцем через Google.
2. Раскройте **Проверка приглашений** и нажмите **Начать проверку**.
3. Нажмите **Проверить доступ** в блоке аккаунта, дождитесь подтверждения.
4. Нажмите **Выйти**, затем снова нажмите кнопку входа Google в этой же вкладке и выберите тот же аккаунт. Страницу не обновляйте и новую запись не начинайте: обычный выход сохраняет текущую запись.
5. Дождитесь подтверждения входа и прежней роли. Затем ещё раз нажмите **Проверить доступ** и дождитесь ответа.
6. Убедитесь, что появилась отметка **Повторный вход тем же аккаунтом: Зафиксировано**. После этого нажмите **Скачать отчёт о доступе**. Файл `tastory-access-….json` можно передать для проверки. Если отметка не появилась, сохраните неполный отчёт и опишите, что показал вход Google.

Этот результат подтверждает повторное получение той же проверенной сервером личности. Отчёт не читает весь реестр `STAGING_AUTH_BINDINGS` и не выдаёт его содержимое. Защита от повторного потребления и уникальность реестра проверяются серверной реализацией и отдельными тестами.

## 2. Неприглашённый аккаунт

Нужен второй Google-аккаунт, которого нет в `STAGING_INVITES`. До этого шага приглашение для него не добавляем. Если Google Cloud ограничивает приложение тестовыми пользователями, сам Google должен разрешать этому аккаунту пройти вход; отказ Google до обращения к Tastory не проверяет приглашения Tastory.

1. Начните новую запись или продолжите ещё не завершённую.
2. Выйдите из Tastory и выберите второй аккаунт через кнопку Google.
3. Ожидается **Доступ не разрешён** без профиля Tastory и отметка **Отказ при входе: Зафиксировано**.
4. Скачайте отчёт.

Записывается именно `ACCESS_DENIED` от Tastory с проверенным requestId. Ошибка сети, истечение токена и отказ самого Google не дают эту отметку. Отчёт не знает, какой аккаунт был выбран при отказе: отсутствие его приглашения подтверждает владелец при выполнении сценария.

## 3. Отзыв у тестового участника и восстановление

Используйте отдельный тестовый аккаунт с ролью `viewer`. Приглашение владельца сохраняйте на всём протяжении проверки. Пароль, Client secret и ID token никому передавать не нужно.

1. В рабочем отдельном проекте **Tastory - Staging API** откройте **Настройки проекта → Свойства скрипта**. Сохраните текущий JSON `STAGING_INVITES` для сверки у себя; не отправляйте полный список в репозиторий.
2. Добавьте только запись тестового аккаунта по [формату приглашения](google-auth-staging.md#пригласить-тестового-участника-или-отозвать-доступ), с ролью `viewer` и будущим `expiresAt`. Остальные записи сохраните. Не меняйте `STAGING_AUTH_BINDINGS`.
3. В Tastory начните запись, войдите тестовым аккаунтом и дождитесь роли **Читатель**. Нажмите **Проверить доступ** и дождитесь подтверждения.
4. В Script Properties удалите только приглашение тестового участника из актуального списка `STAGING_INVITES` и сохраните свойство. Вкладку Tastory оставьте открытой, из аккаунта не выходите.
5. В Tastory нажмите **Проверить доступ**. Ожидается отказ, исчезновение профиля и отметка **Отказ ранее допущенному аккаунту: Зафиксировано**.
6. Восстановите только удалённую запись приглашения, сохранив другие актуальные записи. Привязки `STAGING_AUTH_BINDINGS` не очищайте.
7. Войдите тем же тестовым аккаунтом. Ожидаются роль **Читатель** и отметка **Вход после восстановления приглашения: Зафиксировано**.
8. Скачайте отчёт. После проверки временное приглашение можно убрать, если доступ больше не нужен.

Новый редакторский запуск или публикация Apps Script при изменении приглашений не требуются: текущая политика перечитывается при каждом защищённом запросе. Если любое действие не даёт ожидаемый результат, сохраните неполный отчёт; он не будет превращён в успешный автоматически.

## Что находится в файле

- Версия формата, случайный runId, UTC-время начала и конца, origin без пути/параметров и строка браузера.
- До 30 событий: действие, результат, роль при успехе, requestId, код ошибки и длительность. HTTP-запросы не записываются целиком.
- Аккаунты обозначены `account-1`, `account-2` в пределах одной записи. Имена, почта, Google sub, credentials и тексты серверных ошибок в файл не входят.
- Четыре независимые отметки наблюдённых сценариев. Общего флага «всё успешно» нет: например, отказ при входе сам по себе не доказывает отсутствие приглашения или проверку других браузеров.

Для сопоставления повторного входа внутренние Google ID находятся только в приватной памяти сборщика во время явно включённой записи. Они удаляются при завершении, очистке, достижении лимита или обновлении страницы. Токен по-прежнему очищается при выходе немедленно и в сборщик не передаётся. Экспортированный файл содержит только местные псевдонимы, которые не связывают разные прогоны.

Обычный выход не стирает незавершённый отчёт — иначе нельзя проверить повторный вход. **Очистить отчёт** удаляет только диагностику, сохраняя текущий вход. Обновление страницы очищает и сессию, и отчёт. Остановка или начало нового прогона исключают запоздалые ответы старых запросов из новой записи.

Для подтверждения этапа нужны файлы настоящих прогонов и сведения о выбранных сценариях. Повторение в целевых браузерах и review ADR 0004 остаются отдельными условиями; интерфейс их не помечает выполненными.
